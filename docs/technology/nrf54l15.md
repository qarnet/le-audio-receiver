# Technology: nRF54L15 path

How the nRF54L15 build of this receiver works, in technical but
approachable terms.

## Overview

The nRF54L15 (on the compact **Seeed Xiao** board) is a different
architecture from the nRF5340 build: a single core, a different Bluetooth
controller, and — most importantly — **no dedicated audio PLL**. Nordic's
position is that the nRF54L series lacks the dedicated Audio PLL used to
synchronize a receiving device's playback clock to a transmitter, and is
therefore **not Nordic's ideal/recommended platform for all LE Audio /
audio-streaming uses**; Nordic states that a *subset* of LE Audio use cases
can be supported on the nRF54L series and recommends the nRF5340 for audio
today ([Nordic DevZone: "Is nRF54L15 available to use LE Audio?"](https://devzone.nordicsemi.com/f/nordic-q-a/117778/nrf54l15-support-le-audio)).

This is a scope statement, not a claim that Bluetooth ISO/BAP is impossible:
the transport works, and point-to-point use cases can be fulfilled. Because
the audio clock cannot be steered in hardware, this build compensates for
clock differences in software with a **measure / rate-match** design built
around an asynchronous sample-rate converter (ASRC). This project fully
supports the nRF54L15 as a build target; the caveat is scope, not support.

## Single-core SDC path

Unlike the nRF5340, the nRF54L15 has **one** main core (cpuapp). The
**SoftDevice Controller (SDC)** — Nordic's precompiled Bluetooth link-layer
controller — runs on that same core and is managed by MPSL (the Multi-Protocol
Service Layer). Consequences:

- There is no separate network core and no `hci_ipc` transport image.
- MPSL/SDC **owns the radio peripheral**. Application code must never touch
  radio registers directly; clock measurement uses separate hardware (below).
- The Bluetooth host (BAP/ASCS/PACS), LC3 decode, and the I2S driver all run
  on the same 128 MHz core.

## Fixed audio clock

The nRF54L15 has **no HFCLKAUDIO PLL** (the audio clock the nRF5340 uses to
drive I2S). The I2S peripheral (`i2s20`) is clocked from `PCLK32M`, which
yields an actual LRCK (sample-clock) rate of roughly **47 619 Hz** rather than
exactly 48 000 Hz (the firmware models this as
`CONFIG_AUDIO_I2S_OUTPUT_SAMPLE_RATE_HZ=47619`). The clock cannot be steered in
firmware — the hardware option of trimming it does not exist on this chip.

## Measure / rate-match design

With no steerable clock, the build measures the frequency error and corrects
the audio data path instead:

1. **Measure** (on cpuapp): the Arm cpuapp measures the local PCLK frequency
   against the GRTC (a free-running timer) once per second. A timer peripheral
   (TIMER20) is hardware-snapshotted by a GRTC compare event via GPPI, giving
   an exact tick count per elapsed GRTC interval; the difference yields an
   integer **ppm** (parts per million) frequency error.
2. **Control** (on cpuapp): cpuapp runs the PI (proportional-integral)
   controller. The measured ppm feeds it as a feedforward term, combined with
   a phase term from I2S buffer fill. The output is a ppm correction.
3. **Apply** (on FLPR, or cpuapp as fallback): the correction goes directly
   into the **ASRC** resampling ratio in the audio data path (the actuator is
   a no-op — there is no physical clock to steer).

The render sample rate therefore **tracks the average Bluetooth ISO SDU /
source rate**: when the source is slightly faster or slower, the resampler
ratio is nudged so playback neither underruns nor overruns. This is *rate
matching*, not a claim that the two clocks become identical — the clocks stay
independent; the data path absorbs the difference.

## ASRC and the FLPR offload

The **ASRC** (asynchronous sample-rate converter) is a fixed-point,
linear-interpolation, stereo resampler — no floating point, because the
FLPR has no FPU.

- **Primary path**: the ASRC runs on the **FLPR**, the nRF54L15's
  Nordic-designed RISC-V core (Fast Lightweight Processor), to offload the
  main core. The main core and FLPR exchange audio over shared SRAM rings with
  a handshake/control protocol.
- **Division of labor**: cpuapp performs the measurement and the control
  loop; the FLPR only executes the resampling, using the ppm correction that
  cpuapp supplies. The FLPR does **not** measure the clock or run the
  controller.
- **Fallback**: the identical ASRC implementation runs on cpuapp. If the FLPR
  path faults or is unavailable, the firmware falls back to the cpuapp ASRC
  with no audio drop.
- **Payload contract**: the FLPR ring contract takes **480 input frames** per
  call. Stream shapes that produce a different call size (for example
  **360-frame (7.5 ms)** calls) fall back to cpuapp ASRC — a documented
  limitation, not a failure (see [Known limitations](../known-limitations.md)).

## Limits

- **Point-to-point only**: one source streaming to this receiver works.
  Multi-device synchronization (for example TWS-style synchronized playback
  between two earbuds) is **not** covered by this build. The software drift
  handling above does **not** change that scope: it compensates receiver
  drift for a single point-to-point stream; it is not a substitute for the
  audio PLL that synchronized multi-device use cases rely on.
- **Nordic scope guidance**: as covered in the
  [Overview](#overview), the nRF54L series lacks a dedicated Audio PLL and is
  not Nordic's recommended platform for all LE Audio / audio-streaming uses.
  Nordic guidance is that a subset of LE Audio use cases can be supported.
- No Nordic LE Audio reference application, no LE Audio QDID, no audio PLL —
  the firmware's own measure/rate-match machinery stands in for them (within
  the point-to-point scope).

## Board choice: the Seeed Xiao

The **Seeed Xiao nRF54L15** was chosen because it is small, inexpensive,
broadly available in the hobby market, has an **onboard debugger** (the SAMD11
USB bridge, also used for the serial console) and supports battery charging.
The trade-off is the silicon-level audio-clock limitation above, which this
firmware compensates for in software.

A small board overlay remaps the Xiao's stock pins for this project: the
UART to the SAMD11 USB CDC bridge for the console, and I2S20 to the D0/D1/D2
header pins for the DAC (MCK routed to D3 because the I2S peripheral needs the
PSEL routed even though the DAC does not consume it). See
[Hardware wiring](../hardware-wiring.md).

## Terminology

- **Clock recovery** — the overall loop that keeps playback aligned with the
  source's average rate (measure + control).
- **Drift compensation** — correcting for the continuous small frequency
  difference between source and receiver clocks.
- **Rate matching** — adjusting the audio data path (resampling) rather than
  the clock itself.
- **ASRC** — the asynchronous sample-rate converter that actually resamples
  the PCM to the fixed local clock rate.
