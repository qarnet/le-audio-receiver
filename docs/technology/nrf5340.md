# Technology: nRF5340 path

How the nRF5340 build of this receiver works, in technical but
approachable terms.

## Overview

The nRF5340 is the chip Nordic Semiconductor recommends for LE Audio — it is
the basis of Nordic's LE Audio reference applications. This project mounts the
nRF5340 on a compact **Ebyte E83-2G4M03S** module instead of Nordic's larger
development kit. Audio flows: Bluetooth LE Audio in → LC3 decode → I2S out to
an external DAC, with the chip's dedicated audio PLL keeping playback in sync
with the source.

## Dual-core architecture

The nRF5340 has **two Arm Cortex-M33 cores**:

- **cpuapp** (application core): runs the Zephyr application — the Bluetooth
  LE Audio host (BAP/ASCS/PACS), LC3 decoding, volume control, and the I2S
  driver that feeds the DAC.
- **cpunet** (network core): runs the Bluetooth **link-layer controller**. For
  LE Audio this project uses the Zephyr open-source SW Split controller
  (`BT_LL_SW_SPLIT`) — the ISO-capable open-source controller for the nRF5340.
  (Nordic's own SoftDevice Controller also supports LE Audio on the nRF5340 —
  it is what Nordic's nRF5340 Audio reference application uses — but this
  project's controller runs open source, on the network core.)

The two cores communicate over shared memory using the Zephyr `hci_ipc`
transport: the controller runs on cpunet, the host runs on cpuapp, and HCI
packets (including ISO audio data) cross between them. The network core
firmware is the standard `hci_ipc` image; `sysbuild.cmake` applies the SW Split
controller overlay and configuration to it at build time.

## Audio path

1. **Receive**: ISO audio data arrives at the host via the BAP unicast sink
   (up to two sink ASEs).
2. **Assemble/decode**: SDUs are assembled per ISO stream (two-stream stereo
   "Mode A" or single-stream stereo "Mode B") and decoded with `liblc3` into
   48 kHz stereo PCM.
3. **Volume**: VCP volume/mute is applied (currently a linear scale — see
   [Planned features](../../PLANNED_FEATURES.md)).
4. **I2S out**: PCM is pushed through the Zephyr I2S driver (`i2s0`) to an
   external DAC over a 3-wire connection (BCLK, LRCK, SDOUT; no MCK). See
   [Hardware wiring](../hardware-wiring.md).

## Clock recovery with a dedicated audio PLL

LE Audio sources and this receiver run on independent clocks, so the receiver
must keep its playback rate matched to the average source rate or its buffers
will over- or under-fill. The nRF5340 has a **dedicated audio PLL**
(`HFCLKAUDIO`) — intended for exactly this: tuning the playback clock against
the timing of the received ISO audio stream. It drives the I2S clock and can
be trimmed in firmware.

The design is a PI (proportional-integral) controller:

- A **phase term** measured from I2S buffer fill (how full the playback
  buffer is relative to a setpoint).
- An output in **ppm** (parts per million) that is translated into a
  `HFCLKAUDIO` register trim.

Trimming the audio PLL changes the actual I2S sample rate, which is the
cleanest form of **drift compensation**: the hardware clock itself tracks the
source. On this platform there is no separate frequency measurement input, so
the loop runs phase-only from buffer fill. This is hardware clock steering —
the render clock is adjusted so playback stays aligned with the source's
average SDU rate (the clocks are steered to match, not assumed identical).
This is the same "audio PLL for receiver clock synchronization" role Nordic
describes as missing on the nRF54L series (see the
[nRF54L15 technology note](nrf54l15.md)).

## Board choice: the Ebyte E83 module

Nordic's nRF5340 development kit (DK) is a full evaluation board — large and
priced accordingly. For a hobby build, this project uses the **Ebyte
E83-2G4M03S-TB**, a compact module containing the nRF5340 (with its own
antenna, matching network, and crystal). The trade-off: the module has **no
onboard debug probe**, so flashing requires an **external CMSIS-DAP probe**
(for example a Raspberry Pi Pico running CMSIS-DAP firmware). The repository's
tested flashing path uses OpenOCD built from mainline/master. This is the
module this project found and validated — not a claim that no other compact
nRF5340 modules exist.

## Dual-image flashing constraints

The nRF5340 build is **two firmware images** that must be flashed together:

- the application image (cpuapp), and
- the controller image (cpunet, `hci_ipc` with the SW Split controller).

Flashing is a single dual-core OpenOCD session: it programs the app core,
releases the network core from FORCEOFF, then programs the network core, and
programs the UICR APPROTECT words so debug access stays open across resets.
Details, including recovery, live in [Flashing (developers)](../flashing.md) —
this is developer material.
