# Technology: nRF5340 historical implementation

> **Status: retired historical implementation.** No current nRF5340 receiver
> build, flashing helper, or release asset exists. Original board files and
> helper remain in Git history, not the current tree. This is not supported
> receiver hardware.

Technical reference for the former nRF5340 receiver build.

## Overview

The nRF5340 is the chip Nordic Semiconductor recommends for LE Audio: it is
the basis of Nordic's LE Audio reference applications. The former project
implementation mounted the nRF5340 on a compact **Ebyte E83-2G4M03S** module
instead of Nordic's larger development kit. Audio flowed: Bluetooth LE Audio
in → LC3 decode → I2S out to an external DAC, with the chip's dedicated
audio PLL keeping playback in sync with the source.

## Dual-core architecture

The nRF5340 has **two Arm Cortex-M33 cores**:

- **cpuapp** (application core): ran the Zephyr application: the Bluetooth
  LE Audio host (BAP/ASCS/PACS), LC3 decoding, volume control, and the I2S
  driver that feeds the DAC.
- **cpunet** (network core): ran the Bluetooth **link-layer controller**. For
  LE Audio this project used the Zephyr open-source SW Split controller
  (`BT_LL_SW_SPLIT`), the ISO-capable open-source controller for the nRF5340.
  (Nordic's own SoftDevice Controller also supports LE Audio on the nRF5340:
  it is what Nordic's nRF5340 Audio reference application uses, but this
  project's former controller ran open source, on the network core.)

The two cores communicated over shared memory using the Zephyr `hci_ipc`
transport: the controller ran on cpunet, the host ran on cpuapp, and HCI
packets (including ISO audio data) crossed between them. The network core
firmware was the standard `hci_ipc` image; the old `sysbuild.cmake` applied the
SW Split controller overlay and configuration to it at build time.

## Audio path

1. **Receive**: ISO audio data arrived at the host via the BAP unicast sink
   (up to two sink ASEs).
2. **Assemble/decode**: SDUs were assembled per ISO stream (two-stream stereo
   "Mode A" or single-stream stereo "Mode B") and decoded with `liblc3` into
   48 kHz stereo PCM.
3. **Volume**: VCP volume/mute was applied (a linear scale; see
   [PB-002](../product/backlog/tasks/pb-002%20-%20Use-perceptual-fixed-point-volume-mapping.md)).
4. **I2S out**: PCM was pushed through the Zephyr I2S driver (`i2s0`) to an
   external DAC over a 3-wire connection (BCLK, LRCK, SDOUT; no MCK). See
   [Hardware wiring](../hardware-wiring.md).

## Clock recovery with a dedicated audio PLL

LE Audio sources and the former receiver ran on independent clocks, so the
receiver had to keep its playback rate matched to the average source rate or
its buffers would over- or under-fill. The nRF5340 has a **dedicated audio PLL**
(`HFCLKAUDIO`), intended for exactly this: tuning the playback clock against
the timing of the received ISO audio stream. It drove the I2S clock and was
trimmed in the former firmware.

The former design used a PI (proportional-integral) controller:

- A **phase term** measured from I2S buffer fill (how full the playback
  buffer is relative to a setpoint).
- An output in **ppm** (parts per million) that is translated into a
  `HFCLKAUDIO` register trim.

Trimming the audio PLL changed the actual I2S sample rate: the hardware clock
itself tracked the source for **drift compensation**. On this platform there
was no separate frequency measurement input, so the former loop ran phase-only
from buffer fill. This was hardware clock steering: the render clock was
adjusted so playback stayed aligned with the source's average SDU rate (the
clocks were steered to match, not assumed identical).
This is the same "audio PLL for receiver clock synchronization" role Nordic
describes as missing on the nRF54L series (see the
[nRF54L15 technology note](nrf54l15.md)).

## Historical module: the Ebyte E83

Nordic's nRF5340 development kit (DK) is a full evaluation board: large and
priced accordingly. The former build used the **Ebyte E83-2G4M03S-TB**, a
compact module containing the nRF5340 (with its own antenna, matching network,
and crystal). The trade-off: the module has **no
onboard debug probe**, so flashing requires an **external CMSIS-DAP probe**
(for example a Raspberry Pi Pico running CMSIS-DAP firmware). The historical
tested flashing path used OpenOCD built from mainline/master. This is the
module this project found and validated, not a claim that no other compact
nRF5340 modules exist.

## Dual-image flashing constraints

The former nRF5340 build had **two firmware images** flashed together:

- the application image (cpuapp), and
- the controller image (cpunet, `hci_ipc` with the SW Split controller).

Flashing used a single dual-core OpenOCD session: it programmed the app core,
released the network core from FORCEOFF, then programmed the network core, and
programmed the UICR APPROTECT words so debug access stayed open across resets.
Details, including recovery, remain in the
[historical nRF5340 flashing appendix](../flashing.md#historical-nrf5340-procedure-not-runnable-in-current-tree);
those instructions are not runnable in the current tree.
